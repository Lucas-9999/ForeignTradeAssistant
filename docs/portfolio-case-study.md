# 工程案例：受控的外贸自动化与 CRM

## 问题与目标

客户开发需要保持多来源线索、重复记录、联系状态、回复与跟进的一致性；采集和邮件又有外部副作用。目标是分离业务状态与服务适配器，让操作者可审核，让失败可诊断，让发送与数据库迁移受到约束。

本项目面向 AI 应用开发／自动化工程求职。AI 辅助需求整理、实现、测试与问题定位；代码中保留配置驱动的行业术语 LLM 翻译适配器。本地演示关闭模型调用，未用真实模型服务做验收，不宣称 RAG、模型训练或自主销售代理成果。

## 架构与取舍

- **稳定数据核心**：SQLite 保存线索、标签、分组及沟通记录。显式 schema 门禁划分运行与迁移责任；演示不打开已有业务库。
- **适配器分离**：采集与 SMTP／IMAP 位于不同模块。测试替换网络服务，规则和模板可独立验证。
- **人工与自动化协作**：React 控制台展示业务状态；发送保留配额、统一守卫和一次性授权，界面与服务端共同约束副作用。
- **失败路径可测试**：回归覆盖授权不足、配额、数据库兼容性、提供商失败和状态写入；成功启动不等于邮件已送达。

## 可复现展示

入口使用新建临时数据库和 `data/portfolio-demo.json`，生成 12 条虚构线索及示例时间线。它清除继承的 FTA、LLM、Twilio 配置、禁止 dotenv、清空进程内邮件及第三方凭据、关闭后台任务，只监听 loopback。

只读 ASGI 包装器在路由前拦截写请求；已有数据库路径被拒绝。临时日志句柄在删除本次临时文件前关闭。这些边界由 9 项回归验证，与原测试合计 640 项通过。

原发送守卫、额度和 schema 保护没有被绕过；真实商业材料、运营记录、浏览器登录态和旧 Git 历史不属于作品发布内容。

## AI 辅助工程过程

AI 可以提供实现方案、错误假设和测试草稿，但接受改动需有行为证据。本次案例：Windows 上打开的日志句柄曾导致临时目录清理失败；先用退出回归定位原因，再在入口关闭日志验证修复。

可展示的是代码结构、检查与故障处理过程，没有虚构开发效率、转化增长、模型准确率或真实发送数量。

## 验证与边界

- 640 项 Python 回归通过，包含 9 项演示边界测试。
- 前端构建通过；独立仓库内 lint 实际扫描通过，0 错误、1 条既有 HMR 警告。
- 仅使用临时库、合成记录及提供商替身，没有用真实账号验证发信或采集。
- 剩余构建依赖风险见 `dependency-review.md`，不强制执行不兼容升级。
- 单机 SQLite 和进程内状态不等同于分布式消息系统；多租户或真实生产需要单独设计与验收。

## 面试讨论点

1. 如何把有外部副作用的流程拆成规则、适配器与授权边界。
2. 为什么迁移需要显式门禁，而演示必须隔离已有数据库。
3. 如何把 AI 提出的错误假设转成可重复失败用例，再验证修复。
4. 以后加入 LLM 草稿生成时，如何在人工审核和发送守卫前增加评估、数据最小化与回退；这些是后续设计问题，当前未实现。
